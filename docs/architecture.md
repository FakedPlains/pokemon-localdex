# 架构设计

## 一、目标

这个项目要同时满足三件事：

1. 数据必须完全来自 52Poké Wiki。
2. 数据要能本地离线使用。
3. 查询、队伍构筑、伤害计算必须在多个端上共用一套核心逻辑。

## 二、推荐架构

采用 `采集层 -> 标准化层 -> 本地 API 层 -> 多端展示层` 的四层结构。

### 1. 采集层

职责：

- 抓取 52Poké 页面
- 记录抓取时间、URL、页面标题
- 保存原始 HTML 到 `data/raw/`

原则：

- 不直接把页面内容喂给前端
- 所有解析逻辑都集中在 `packages/scraper`

### 2. 标准化层

职责：

- 把 wiki 页面转换为统一结构
- 统一多世代字段命名
- 解决别名、形态、地区形态、超极巨化、悖谬种等特殊情况

核心实体：

- `PokemonSpecies`
- `PokemonForm`
- `PokemonGenerationRecord`
- `Item`
- `Ability`
- `Move`
- `TypeChart`
- `BattleTeam`

### 3. 本地 API 层

职责：

- 提供统一查询入口
- 给 Web、小程序、未来 App 共用
- 屏蔽底层 JSON / SQLite 的差异

建议接口：

- `GET /pokemon`
- `GET /pokemon/:id`
- `GET /items`
- `GET /items/:id`
- `GET /teams`
- `POST /teams`
- `POST /battle/damage`

### 4. 展示层

建议拆法：

- `apps/web`：优先实现，兼容 PC 和手机浏览器
- `apps/weapp`：微信小程序
- App：后续可基于同一套 API 和共享核心接入 Taro RN 或独立移动容器

## 三、为什么不建议一开始就三端同时重做 UI

你真正复杂的部分不在界面，而在：

- 52Poké 页面结构不完全标准化
- 宝可梦跨世代字段变化很多
- 对战伤害计算需要一套稳定的领域模型

所以优先级应该是：

1. 数据模型正确
2. 采集解析稳定
3. API 清晰
4. 再铺 UI

## 四、MVP 范围

第一阶段只做：

- 宝可梦基础资料
- 道具资料
- 队伍保存
- 单次伤害计算

第二阶段再补：

- 招式、特性、属性克制
- 性格、努力值、个体值编辑器
- 双打、天气、场地、墙、道具、特性联动
- 图鉴筛选和高级检索

## 五、数据落地建议

推荐双存储：

- 开发期：JSON，便于调试
- 正式本地库：SQLite，便于检索和索引

原因：

- JSON 可读性强，适合调试采集结果
- SQLite 更适合多条件查询、分页、模糊搜索和队伍持久化
